# 🔍 TDD
**Test Driven Development** 
- 동작하는 코드를 작성하기 이전에 테스트를 먼저 작성하고, 그 테스트를 통과하는 코드를 작성함으로써 테스트된 동작하는 코드를 얻는 개발 방법   
👉🏻 테스트 코드를 먼저 작성한 후, **실제 개발 코드 작성**

## ✔️ TDD 개발 방식
1. **RED**
    - 프로덕션 코드가 없는 상황에서 실패하는 테스트 코드 먼저 작성   
    👉🏻 필요한 테스트 로직을 작성하고, 실제 개발 코드는 작성되어 있지 않기 때문에 당연히 컴파일이 안되므로 **에러 발생**
    ```java
    @Test
    void testSum() {
        Calculator calculator = new Calculator(); 
        int result = calculator.add(2, 3); 
        assertEquals(5, result); 
    }
    ```
    - 위 코드는 테스트를 진행할 로직은 잘 작성되어 있음
    - 하지만 프로덕션 코드 `Calculator`가 작성되어 있지 않기 때문에 에러 발생 = **`RED`**    
    👉🏻 테스트 코드를 먼저 작성하는 이유는 <u>쉽게 발견하기 어려운 예외 케이스를 놓치지 않게 해주고, 구현에 대한 빠른 피드백을 통해 과감한 리팩토링이 가능</u>
2. **GREEN**
    - 실패하는 테스트 코드를 통과하기 위해 프로덕션 코드에서 최소한의 코드를 작성성
    - 테스트 코드가 컴파일되고 실행까지 정상적으로 되도록 코드를 작성한 후, 후에 테스트의 보호 아래 코드를 다듬는 것
    ```java
    public class Calculator {
        public int add(int a, int b) {
            return a + b;
        }
    }
    ```
    - 위 코드는 이전에 작성되지 않은 프로덕션 코드를 작성한 것 = **`GREEN`**
    - 이전에 RED 과정에서 진행한 테스트 코드는 위 프로덕션 코드를 작성함으로써 정상적으로 돌아감
3. **REFACTOR**
    - 프로덕션 코드를 좋은 코드로 개선

👉🏻 해당 과정을 통해 실제 코드에 대해 기대되는 바를 명확하게 정의함으로써 불필요한 설계를 피할 수 있고, 정확한 요구 사항에 집중할 수 있다

## ✔️ 테스트의 종류
### Unit Test
- 전체 코드 중 **작은 부분을 테스트**하는 것
- 기본적으로 테스트를 위한 입력 값을 주고, 그에 대한 함수의 출력 값이 예상과 일치하는지를 파단하는 것이 유닛 테스트  
- JUnit5를 통해 단위로 테스트를 작성하고 실행함
- AssertJ를 통해 단위 테스트에서 결과가 예상대로 일치하는지 비교하고 검증
```java
    @Test
    void testSum() {
        Calculator calculator = new Calculator(); 
        int result = calculator.add(2, 3); 
        assertThat(result).isEqualTo(5);
    }
```
👉🏻 다른 유닛과 격리된 상태에서 독립적으로 테스트를 진행하기 때문에 실패 원인을 명확하게 알 수 있고, 짧은 시간 내에 테스트를 마칠 수 있음    
👉🏻 하지만 사용자가 소프트웨어와 상호작용하는 과정에서 실패를 하더라도, 해당 테스트는 통과할 수 있음 
### Integration Test
- 여러 유닛이 함께 작동하는 방식을 테스트 해서, 유닛 간의 상호 작용을 테스트
- 컴포넌트 간의 상호 작용 혹은 마이크로 서비스 간의 상호 작용을 테스트
### Functional Test
- 소프트웨어의 특정 기능 혹은 동작을 테스트
- 유저 플로우와 연관된 모든 단위를 포함하여 테스트   
👉🏻 사용자가 소프트웨어와 상호 작용하는 관계와 밀접하기에, 테스트가 매우 견고    
👉🏻 하지만 테스트가 독립적이지 않고, 여러 요소와 결합된 형태이기에 실패 시 어디서 오류가 났는지 찾기 어려움 

## ✔️ 좋은 테스트의 특징 : FIRST 
- **F**ast : 테스트는 빠르게 동작하여 자주 돌릴 수 있어야 함
- **I**ndependent : 각각의 테스트는 독립적이며 서로 의존해서는 안됨
- **R**epeatalbe : 어느 환경에서도 반복 가능해야 함
- **S**elf-Validating : 테스트 성공 또는 실패를 bool값으로 결과 내어 자체적으로 검증되어야 함
- **T**imely : 테스트하려는 실제 코드를 구현하기 직전에 구현해야 함    

👉🏻 좋은 테스트는 빠르게 독립적으로 어느 환경에서든 실행이 가능하고 검증할 수 있어야 함 

## ✔️ Spring에서 TDD 프로그래밍 방법
- 레이어드 아키텍쳐 형식으로, 관심사를 분리해서 책임을 나누고 유지보수하기 용이하게 만들어 접근
- `Repository 계층의 테스트` = **Persistence Layer** 👉🏻 데이터베이스와의 상호작용을 검증
    - H2와 같은 인메모리 데이터베이스 기반의 통합 테스트로 진행
    - `@DataJpaTest` 기준으로 작성
    - CRUD와 같은 데이터 처리 부분에 대해서만 테스트
    ```java
    @DataJpaTest
    class UserJpaRepositoryTest {

        @Autowired
        private UserJpaRepository userJpaRepository;

        @Test
        void testSaveAndFindByUserId() {
            User user = User.builder()
                    .name("test-user")
                    .email("test-user@mail.com")
                    .build();

            userJpaRepository.save(user);

            Optional<User> savedUser = userJpaRepository.findById(user.getId());

            assertThat(savedUser.get().getName()).isEqualTo("test-user");
        }
    }
    ```
- `Service 계층의 테스트` = **Business Layer** 👉🏻 비즈니스 로직을 검증
    - Mockito를 사용해 Repository 계층을 Mocking하여 실제 DB와 상호 작용하지 않도록 하며, 비즈니스 로직만 검증
        - `@Mock`을 사용하면, userJpaRepository가 실제 DB와 연결되거나 save 메서드가 실제로 실행되지 않고, 가짜 객체를 사용하여 메서드를 지정한 대로 동작
        - `@InjectMocks`을 사용하여 Mock 객체들을 userService에 주입하여, 실제 테스트할 대상인 UserService의 인스턴스를 자동으로 생성하고 의존성을 주입
    - Persistence Layer를 주입받는 통합 테스트를 진행
    - `@SpringBootTest`를 기준으로 작성하며 수동으로 삭제하는 tearDown메서드를 활용
    ```java
    @SpringBootTest
    class UserServiceTest {

        @Mock
        private UserJpaRepository userJpaRepository;

        @InjectMocks
        private UserService userService;

        @Test
        void testSaveAndFindByUserId() {
            User user = User.builder()
                    .name("test-user")
                    .email("test-user@mail.com")
                    .build();

            Mockito.when(userJpaRepository.save(Mockito.argThat(u -> u.getName().equals("test-user") && u.getEmail().equals("test-user@mail.com"))))
                    .thenReturn(user);

            User savedUser = userService.saveUserData(user.getName(), user.getEmail());
            assertThat(savedUser.getName()).isEqualTo("test-user");
        }
    }
    ```
- `Controller 계층의 테스트`= **Presentation Layer** 👉🏻 HTTP 요청과 응답 처리 로직을 검증
    - SpringTest MockMvc를 사용해 진행 
    - Business Layer와 Persistence Layer를 Mocking 처리하여 테스트를 진행
    - `@WebMvcTest`를 사용하여 Controller만을 테스트
    ```java
    @WebMvcTest(UserController.class)  
    class UserControllerTest {

        @Autowired
        private MockMvc mockMvc;

        @TestConfiguration
        static class UserServiceTestConfig {

            @Mock
            private UserService userService;

            @InjectMocks
            private UserController userController;

            @Bean
            public UserService userServiceMock() {
                UserService userService = Mockito.mock(UserService.class);
                Mockito.when(userService.saveUserData("test-user", "test-user@mail.com"))
                        .thenReturn(User.builder().name("test-user").email("test-user@mail.com").build());
                return userService;
            }
        }

        @Test
        void testSaveUser() throws Exception {
            mockMvc.perform(post("/user/save")
                            .contentType(MediaType.APPLICATION_JSON)
                            .content("{\"name\":\"test-user\", \"email\":\"test-user@mail.com\"}"))
                    .andExpect(status().isOk())
                    .andExpect(jsonPath("$.name").value("test-user"))
                    .andExpect(jsonPath("$.email").value("test-user@mail.com"));
        }
    }
    ```


**BDD 스타일로 작성**
- Behavior Driven Development
    - 함수 단위의 테스트에 집중하기 보다 시나리오에 기반한 테스트 케이스 자체에 집중하여 테스트 ➡️ 개발자가 아닌 사람이 봐도 이해할 수 있을 정도의 추상화 수준 권장
- `GIVEN` : 시나리오 테스트에 필요한 객체와 행위 준비 (객체, 값, 상태)
- `WHEN` : 시나리오 수행을 하는 단계 (메서드 호출)
- `THEN` : 시나리오 진행에 대한 결과를 검증하는 단계 (AssertJ)
> 어떤 환경에서 (GIVEN)  
> 어떤 행동을 진행했을 때 (WHEN)    
> 어떤 상태 변화가 일어난다 (THEN)
